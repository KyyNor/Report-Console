Agent 工作台优先化与服务化演进方案

目标不是把已有的 CPT 开发能力再包一层聊天，而是把它变成可定位、可验证、可审计、可迁移的项目开发工作台；Electron 继续是近期主交付形态，同时为 Web 部署保留正确边界。

先给结论

你的调整方向是对的，而且比“每个资源详情页里放一个 用 Agent 做 按钮”更符合这个产品的核心价值：资源浏览器负责定位和核查，右栏的默认任务是持续协作与编排。

推荐的主模型：工作台右栏默认是当前项目的 Agent 会话；点击资源时右栏临时切为详情；详情右上角关闭后立即回到同一个、未卸载的会话。资源通过“附加”成为轻量引用，而不是把正文塞进提示词。

“附加”不是发送一段提示词

现在的上下文提示词已经是正确的最小雏形：告诉 Agent 当前项目、当前资源，以及应当调用什么工具。下一步应把它从一次性自然语言升级为结构化、可见、可删除、可持久化的引用。

ContextRef {
  projectId: 'frdemo',
  kind: 'dataset' | 'page' | 'procedure' | 'doc' | 'traditional-cpt',
  name: 'book_by_id',
  lookup: 'read_dataset',
  revision: 'updatedAt（可选）'
}
  • 界面：输入框上方显示引用 chip；可移除，可从资源列表“一键附加”，不应自动发送消息。
  • @：用于资源引用。先选类别（接口、页面、过程、文档、传统 CPT），再按名称过滤；默认只列当前项目。
  • 发送时：运行时把引用转成“该资源在当前项目；先调用工具 Y 获取现状”的隐藏上下文/开发者消息；只有 Agent 真正调用读取工具时才加载正文。传统 CPT 仅提示先查概览，再按需查数据集、参数、组件、脚本或引用。
  • 安全：引用不能成为绕过项目边界的参数。服务端依据会话 scope 校验 projectId 与资源归属。
已落地的按需读取：read_dataset(project, name) 用于单接口；inspect_legacy_cpt(path, view, query, cursor, limit) 仅返回传统 CPT 的结构化、分页摘要，不提供整份 XML。这样既能让 Agent 借鉴旧页面，又不会用大文件挤占上下文。

当前 Agent 设计：已具备什么能力

代码审查结果：Agent 本体运行在渲染层的 pi 引擎中；工具定义由主进程导出，实际工具执行经 IPC 回到主进程。因此 CPT 质量门、SQL 审计和写入确认没有被模型绕过。会话目前存于渲染端 IndexedDB，并由 Agent 页与工作台右栏共享。

能力组调整后的工具评价
环境与项目不向 Agent 暴露全局项目/连接发现或建项目能力项目由界面选择，避免模型把“找工作区”当成开发步骤，也消除跨项目发现入口。
数据接口list_datasets、read_dataset、save_dataset、delete_dataset、build_data_cpt、test_datasetbuild_data_cpt 在成功后自动验证安全的只读接口；写接口仍需显式测试，避免产生副作用。
存储过程list_procedures、read_procedure、save_procedure、apply_procedure保留当前项目内的定义与应用；跨项目关联是人工治理动作，不交给 Agent。
文档、页面与传统 CPTlist_docs、read_doc、write_doc、list_pages、read_page、write_page、create_page、update_page_paths、build_page、open_page、inspect_legacy_cpt页面产物位置可安全调整；传统 CPT 仅能在当前项目内读取结构摘要。
数据库sql_query、sql_exec、list_tables、describe_table读写通道受控，并限制为当前项目已绑定的连接；不接受任意跨库 database 参数。

能否直接在 Agent 里完成报表？

可以。当前工具集已经覆盖“数据接口、存储过程、页面、构建、实测、预览”的完整主链路。更准确地说，Agent 应作为任务编排入口，而资源详情页应作为核查、手工微调和证据查看入口。对于“修改一个页面及相关数据”，推荐在该项目的 Agent 会话中附加页面与相关接口，再明确目标；Agent 应先读取、给出变更计划，再依次更新和验证。

项目隔离：当前事实与必须补的边界

已有

可迁移资源归属

项目根的 project.yaml 保存受管页面/数据 CPT 与接口/过程契约；SQLite 仅维护本机注册、环境、连接与运行历史。传统 CPT 不进入清单。

本轮补齐

Agent 访问隔离

会话按项目创建；工具执行前由桥接层覆盖项目参数，SQL 连接只能是当前项目绑定连接，并禁止任意 database 参数。

本轮后的回答：在 A 项目中启动的 Agent 只能调用 A 的项目资源及其绑定连接；工具桥接层会忽略模型传入的项目名，并拒绝不在 A 绑定清单内的连接。B 项目的资源不会被列出、读取或修改。

建议的作用域模型

ExecutionContext {
  actorId, workspaceId,
  projectId,                         // 当前工作范围，必填
  allowedConnectionIds,              // 由项目绑定关系推导，不接收模型声明
  crossProject: 'deny',
  sessionId, requestId
}

executeTool(context, toolName, args)
  → authorize(context, toolName, args)
  → service.useCase(context, args)
  → audit(context, result)
  • Agent 会话默认一项目一个 scope；切换项目时切换会话，或明确提示“此会话属于 A”。
  • 工具不再相信模型传来的 project；执行层注入当前项目。跨项目过程关联保留为人工界面动作，而非 Agent 权限。
  • SQL 的连接必须由当前项目的绑定连接集合验证；跨库访问另设明确授权，而不是让 database 任意切换。
  • 未来服务端应从登录身份推导 actor/workspace/project scope；不要把当前渲染层传入的 scope 当作多用户安全边界。

路径收敛已完成：项目清单使用项目内相对路径，页面服务按受管清单解析 jsx/mjs/cpt；默认的 data/pages/meta 只是新建项目布局。服务化时仍建议抽出 ProjectArtifactStore.resolve(projectId)，让 IPC 与 HTTP 共用同一条授权和文件路径边界。

用 Agent 完成一个报表：推荐的真实流程

1. 定位与需求选择项目；附加需求文档、已有页面或接口。Agent 读取文档与当前资源，不直接猜测。
2. 数据摸底读取项目资源；必要时 describe_table / 只读查询确认表结构。
3. 数据层先行需要时建表/保存并应用过程；保存接口契约；构建 _data.cpt 后自动验证安全的只读接口；写接口在确认后实测。
4. 页面层创建或读取 JSX；实现页面；构建页面 CPT；打开预览。
5. 验收与沉淀验证全部数据接口、关键页面预览；将设计决策写入 meta 文档；保留构建与审计证据。

推荐对话方式

直接在项目 Agent 对话中描述目标即可，例如“基于 @需求文档 与 @页面，新增图书编辑能力；先给出影响范围和计划，确认后执行”。

对有副作用的操作，Agent 应先声明计划并用只读工具核对；实际 DDL/DML 已要求 confirm: true 且落审计，但未来仍应加入产品级确认卡片，而不是只依赖模型传参。

资源详情页的定位

不是另一个对话入口，而是“证据与微调页”：看 SQL/代码、查看构建与实测记录、手动保存、打开预览、附加给 Agent。这样能避免对话与详情页面争夺同一个右栏的主身份。

界面优化：结合新主模型的取舍

整体 UI 已有一致的浅色技术工具语言：顶部导航、蓝色主操作、深色代码区、资源状态标签和编辑器的方向一致。优先级应从“美化卡片”转到“让 Agent 工作区成为稳定中心”。

优先级观察方案
P0详情页里的“用 Agent 做”与构建/保存/实测同列，入口分散且层级相近。右栏默认 Agent；资源改为“附加”动作。详情关闭回对话，Agent 入口只保留全局导航与右栏默认态。
P0当前 Agent 页面在超宽屏中用户/助手消息横向距离很大，推理虚线块比正文更显眼。对话列固定并居中；默认折叠推理；工具结果保持紧凑。右栏模式下使用同一套密度更高的组件。
P1三栏工作台在单项目情况下左栏与中栏较占宽，资源列表压缩了任务区。左栏可折叠；中栏支持拖拽宽度；右栏设合理最小宽度。资源列表提供行尾附加图标或悬浮菜单。
P1连接页和设置页在超宽屏的有效内容偏左，右边大面积留白。使用居中 max-width，或采用真正有信息价值的双栏；保存操作做成吸附页脚/标题栏，并显示未保存状态。
P2资源组、资源行、卡片和提示条的边线密集；成功状态也多重重复。弱化次级分割线，以留白和浅底色分组；默认仅显示主状态，详情再展开实测行数和耗时。
可访问性检查项：浅灰辅助文字与浅蓝选中态需实测对比度；没有文字的删除/设置图标需 Tooltip、可读标签和至少 32px 点击面积；窄屏和键盘焦点需要运行态验证，截图无法确认。

前后端分离 + Electron 壳：可行，而且应当这样演进

可行，但不要把“Electron 主进程”简单改名为“后端”。真正应该先抽离的是业务 use case 和基础设施端口；IPC 只是第一种 transport，未来 HTTP/SSE 是第二种 transport。Electron 仍可作为近期首要发布目标，并改为同一 Web 前端的打包壳。

必须做出的部署选择

构建 CPT 必须写入 FineReport 可读取的 reportlets 目录；所以未来 B/S 模式让服务端与 FineReport 同机或同一受控部署单元，服务端直接持有 reportlets、FineReport Client 与数据库访问。浏览器和 Electron 壳都不再依赖本地 FineReport、报表目录或数据库资源。

多环境平台浏览器 / Electron 壳每个环境各自部署 FineReport 与应用服务多项目、多人、受控部署

不推倒重来的实施路线

Phase 0 · 完成
边界、路径和清单已经收敛
Agent 强制当前项目与允许连接；project.yaml 管理受管产物与契约；页面路径可安全调整；传统 CPT 与受管产物被隔离。
Phase 1 · 完成主体
Agent-first 工作台已落地
右栏默认会话、详情临时覆盖、资源附加、仅 @ 联想和每项目作用域已完成。下一步可补产品级危险操作确认与更完整的会话草稿/滚动位置保持。
Phase 2
提取应用核心
从 src/main 中抽出 project/dataset/page/procedure/build/test use case；把 SQLite、文件、FineReport、MySQL 实现放到 adapter；保留 IPC adapter，行为不变。
Phase 3
增加服务 API
用同一 use case 增加 HTTP API 与 SSE Agent 事件流；React 改为 API client；会话、密钥、审批和 FineReport/数据库访问迁到服务端。Electron 壳连接该服务。
Phase 4
准备多人/远端
认证、workspace/tenant、RBAC、密钥托管、任务队列与部署健康检查；每个环境由服务端部署 FineReport 与应用服务。此阶段再决定 Postgres/对象存储等基础设施。
Phase 5
双形态发布
同一前端产物可在 Web 部署；Electron 仅提供桌面窗口、协议唤起、更新和本地缓存等壳能力，不再承担本地资源执行。

建议的决策顺序

  1. 确认“每项目一个默认 Agent scope；右栏默认 Agent；详情可关闭返回”的交互原则。
  2. 跨项目策略固定为默认拒绝；关联外部过程仅由人工界面完成。
  3. 将已完成的 Phase 0/1 作为稳定基线，继续观察真实项目迁移与传统 CPT 查阅的使用体验。
  4. 从 Phase 2 开始抽服务边界，仍以 Electron 打包为主，不改变用户的安装与使用方式。
  5. 只有在明确需要浏览器多人使用或远端部署时，再进入 Phase 3 以后的服务化投资。
